# 위치 전송 빈도 시험 (시뮬레이터)

- 시험일: 2026-10-24
- 결론: **시뮬레이터에서는 15m / 10초 설정으로 정류장 방문을 놓치지 않았다 (통과 10회, 40/40). 실기기는 아직 측정하지 못했다.**
- 관련: `driver_app/ISSUE.md` "위치 전송 설정 변경", `docs/future-improvements.md` 18번·21번

## 1. 왜 시험했나

정류장 도착·출발은 "버스가 정류장 영역(한 변 30m의 네모) 안에 들어갔다/나갔다"를 Traccar가 판단해서 알려 주는 것으로 기록한다. 그러려면 **운전자 폰이 보낸 위치가 정류장 영역 안에 최소 한 번은 찍혀야** 한다. 위치를 너무 성기게 보내면 영역을 지나가는데도 위치가 한 번도 안 찍혀 방문이 빠진다. 방문이 하나라도 빠지면 승객 화면의 해당 정류장이 틀리게 보인다.

운전자 앱의 위치 전송 설정은 이 문제를 줄이려고 다음 값으로 바꿨다 (`driver_app/lib/tracking_controller.dart`).

| 항목 | 값 | 뜻 |
|---|---|---|
| 거리 기준 | 15m | 15m 움직일 때마다 위치를 보낸다 |
| 시간 기준 | 10초 | 10초마다 위치를 보낸다 |
| 정지 시 | 30초 | 멈춰 있어도 30초 안에는 보낸다 |

이 값이 실제로 정류장을 놓치지 않는지 확인하는 것이 이 시험의 목적이다.

## 2. 시험 환경과 방법

| 항목 | 내용 |
|---|---|
| 앱 | `driver_app` 디버그 빌드, iOS 시뮬레이터(iPhone 17, iOS 26.5), Flutter 3.47.4 |
| 서버 | Docker 한 대에서 Rails와 Traccar 실행(`docker compose up`) |
| 차량·노선 | 시드 데이터의 1001 차량, 1번 노선(정류장 4곳: 고성터미널 → 고성시장 → 고성병원 → 고성고등학교) |
| 경로 | 첫 정류장 100m 앞에서 시작해 마지막 정류장 80m 뒤에서 끝나는 약 1.1km의 직선 |
| 위치 공급 | `xcrun simctl location <기기> start --speed=<m/s> --interval=1 <좌표들>` — 시뮬레이터가 위치를 **1초마다** 앱에 넣는다 |
| 준비 | 앱에서 "운행 시작"을 누른 상태(서버에 열린 운행이 있음)에서 시작 |

한 번의 통과 절차는 다음과 같다.

1. 위치를 경로 시작점으로 옮기고 15초 기다린다(앞 통과의 영향을 끊는다).
2. 정해진 속도로 경로를 따라 움직인다.
3. 끝난 뒤 20초 더 기다려 늦게 도착하는 이벤트를 받는다.
4. 그 시간대(시작~끝+20초)에 서버에 기록된 정류장 방문을 센다.

판정 기준: 한 번의 통과에서 **4곳 모두 진입과 이탈이 기록**되면 성공이다(진입 4건 + 이탈 4건). 정류장이 하나라도 빠지거나 한 정류장이 두 번 기록되면 실패다.

## 3. 시험 조건과 결과

| 속도 | 정류장 중심에서 벗어난 거리 | 통과 | 진입 | 이탈 | 중복 |
|---|---|---|---|---|---|
| 5 m/s (18 km/h) | 0m (중심선) | 2회 | 4/4, 4/4 | 4/4, 4/4 | 없음 |
| 10 m/s (36 km/h) | 0m | 2회 | 4/4, 4/4 | 4/4, 4/4 | 없음 |
| 20 m/s (72 km/h) | 0m | 2회 | 4/4, 4/4 | 4/4, 4/4 | 없음 |
| 10 m/s | 10m 비껴감 | 2회 | 4/4, 4/4 | 4/4, 4/4 | 없음 |
| 20 m/s | 10m 비껴감 | 2회 | 4/4, 4/4 | 4/4, 4/4 | 없음 |

- **합계**: 통과 10회, 정류장 방문 40건 중 40건 기록(진입·이탈 모두), 누락 0건, 중복 0건.
- 정류장 영역의 반폭이 15m라서, 10m 비껴가도 영역 안을 지난다. (그보다 더 벗어나는 경우는 시험하지 않았다.)

## 4. 결론

1. **15m / 10초 설정은 시뮬레이터 조건에서 72km/h까지 충분했다.** 속도와 상관없이 결과가 같았으므로 이 설정이 병목은 아니었다.
2. 이 설정을 지금 바꿀 필요는 없다. 그대로 쓰고 **실기기 시험에서 다시 확인**한다.

### 이 시험이 보장하지 않는 것

시험 조건이 실제보다 훨씬 쉽다. 그래서 "충분하다"가 아니라 "시뮬레이터에서는 문제가 없었다"까지만 말할 수 있다.

| 한계 | 설명 |
|---|---|
| 위치가 이상적이다 | 시뮬레이터 위치는 오차 없는 직선이고 1초마다 정확히 온다. 실제 GPS는 수 m~수십 m 오차가 있고 튀거나 끊긴다 |
| 고속 구간 | 20 m/s에서 1초에 20m 움직여 영역(30m) 안에 위치가 1~2번 찍힌다. 30 m/s(108km/h) 이상이면 놓칠 수 있으나 시내버스에서는 드물어 시험하지 않았다 |
| 정류장 정차 | 모든 통과가 멈춤 없이 지나가는 것이었다. 정류장에 서는 경우(위치가 한곳에 모임)는 시험하지 않았다 |
| 영역에서 더 벗어남 | 중심에서 10m까지만 확인했다. 도로 폭이나 GPS 오차로 15m 이상 벗어나면 영역을 아예 지나지 않을 수 있다 |
| 백그라운드·화면 꺼짐 | 시뮬레이터는 앱이 앞에 떠 있는 상태였다. 실제 폰은 화면이 꺼지거나 다른 앱을 쓰는 동안 위치 전송이 줄 수 있다 |
| 배터리·열 | 측정하지 않았다 |
| 통신 끊김 | 오프라인에서 모아 두었다가 늦게 보내면 이벤트가 만들어지지 않는다 (`future-improvements.md` 18번) |

### 실기기 시험에서 확인할 것

- 정류장 4곳을 실제로 통과(정차 포함)하는 운행을 여러 번 반복해 방문이 빠지는 정류장이 있는지 본다.
- 빠진 방문은 Traccar가 받은 위치가 영역 안에 있었는지로 원인을 가른다. 위치가 영역 안에 없었다면 전송 설정이나 GPS 정확도 문제이고, 있었는데 방문이 없다면 이벤트 포워딩 문제다.
- 화면을 끄고 주머니에 넣은 상태, 다른 앱을 쓰는 상태에서 같은 시험을 한다.
- 그때 놓치는 정류장이 생기면 15m → 10m, 10초 → 5초를 먼저 검토한다 (배터리 영향과 맞바꿈).

## 5. 다시 시험하는 방법

1. `docker compose up -d`로 서버를 올리고, 시뮬레이터에서 앱을 등록한 뒤 "운행 시작"을 누른다. 시험이 끝날 때까지 **앱에서 운행을 종료하지 않는다.**
2. 경로 좌표(1번 노선): `34.97246,128.32143` → `34.9731,128.3222` → `34.9751,128.3246` → `34.9771,128.3270` → `34.9791,128.3294` → `34.97961,128.33002`
3. 시작점으로 위치를 옮기고 15초 기다린 뒤 이동한다.
   ```
   xcrun simctl location booted set 34.97246,128.32143
   xcrun simctl location booted start --speed=10 --interval=1 \
     34.97246,128.32143 34.9731,128.3222 34.9751,128.3246 34.9771,128.3270 34.9791,128.3294 34.97961,128.33002
   ```
4. 끝난 뒤 20초 기다리고, 그 시간대의 방문 기록을 센다(관리자 대시보드의 "최근 정류장 방문", 또는 서버 로그의 `[StopVisitRecorder] recorded …`). 끝나면 `xcrun simctl location booted clear`.
5. 속도(`--speed`)를 바꿔 반복한다. 반복 횟수가 많으면 위 절차를 스크립트로 묶어 쓴다.

### 시험하면서 얻은 주의점

- **운행이 열려 있어야 한다.** 첫 시도에서는 앞 시나리오 시험에서 운행이 이미 종료되어 있었고, 진행 중인 운행이 없는 차량의 신호는 서버가 무시하므로 14회 통과 모두 방문 0건이 나왔다. 설정 문제가 아니라 시험이 무효였다. 이후 매 통과 전에 열린 운행을 확인하게 했다.
- **통과 사이 위치를 시작점으로 옮기고 기다린다.** 끝점에서 바로 시작점으로 가면 위치가 순간이동해 이상한 이벤트가 생길 수 있다.
- `--interval`을 1초보다 짧게 주면 위치 시각이 실제 시각보다 앞서 가서 첫 정류장이 기록되지 않는다 (`lib/tasks/demo.rake`도 같은 이유로 1초 미만을 막는다).
