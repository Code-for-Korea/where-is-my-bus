# 설계: 실시간 운행 안내 (N분 후 도착)

- 목표: 승객 화면에 "정차 중 / 곧 도착 / N분 후 도착 / 이동중"을 보여준다.
- 상태: **방식 A 구현됨(2026-11-13), 방식 B는 미구현.** 구현 내용과 설계에서 달라진 점은 11절. 팀 합의가 필요한 항목은 9절.
- 배경: 이벤트 기반 재작성(`docs/design-event-driven-rewrite.md`)에서 ETA와 GPS 로그를 일부러 뺐다. 이 문서는 그것을 다시 넣는 방법이다.

## 1. 현재 상태

| 항목 | 현재 |
|---|---|
| 위치 수집 | 운전자 앱 → Traccar(5055). 15m 이동 또는 10초마다 전송 |
| Rails가 받는 것 | Geofence 진입·이탈 이벤트만 (`POST /integrations/traccar/events`) |
| Rails가 저장하는 것 | 정류장 방문 기록(`stop_visits`: `entered_at`, `exited_at`) |
| 승객 화면 | `RouteBusStatuses`가 방문 기록으로 `arriving`(정차 중) / `approaching`(N개 정류장 남음) / `unknown`(위치 확인 중) / `passed`를 계산 |
| 좌표 | Rails는 좌표를 받지 않는다. 정류장 사이를 이동하는 동안 서버가 아는 것이 없다 |

예전 ETA(`RouteProgress`)의 문제는 다시 만들지 않아야 한다 (`docs/business-logic-review.md`).

- GPS 신선도 검사가 없어 꺼진 단말의 마지막 위치가 계속 "현재 위치"로 쓰였다.
- 목표 정류장을 이미 지나간 버스가 "0분"으로 나왔다.
- `sequence`에 중복·결번이 있으면 이웃 정류장 계산이 어긋났다.

## 2. 두 가지 방식

### 방식 A — 방문 기록으로 추정 (좌표 없음)

`stop_visits`에 이미 쌓이는 시각만으로 구간 소요 시간을 배우고, 그 합으로 도착 시각을 추정한다.

1. **구간 통계**: 같은 노선의 인접 정류장 쌍(A→B)마다 과거 운행의 "A 이탈 → B 진입" 시간을 모아 중앙값을 낸다. 정차 시간("진입 → 이탈")도 정류장별로 같은 방식으로 모은다.
2. **추정**: 마지막 방문이 닫혀 있으면(막 출발) `max(현재 구간 중앙값 − 출발 후 경과, 하한)` + 이후 구간들의 (중앙값 + 정차 시간) 합. 열려 있으면(정차 중) 남은 정차 시간부터 센다.
3. **콜드스타트**: 표본이 부족한 구간이 경로에 하나라도 있으면 ETA를 내지 않고 "N개 정류장 남음"으로 폴백한다. 거리 기반 가정 속도로 메우는 안은 처음 구현에서 뺐다(11절).

| 장점 | 한계 |
|---|---|
| Traccar·앱 변경 없음, 서버 부하 증가 없음 | 정류장 사이에서는 갱신이 없다 |
| 위치 신선도 문제가 없다 | 첫 며칠은 통계가 없어 추정이 거칠다 |
| 기존 이벤트 흐름을 그대로 쓴다 | 신호·정체로 구간 시간이 흔들린다 |

### 방식 B — 실시간 위치로 거리 기반 계산

Traccar가 Rails로 위치를 직접 전달하게 하고, 남은 거리를 구간 평균 속도로 나눈다.

1. **전달**: Traccar의 위치 전달 설정(position forwarding)으로 모든 위치를 Rails에 보낸다. 이벤트용 `EVENT_FORWARD_*`와 별개 설정이다.
2. **저장**: 차량당 최신 한 건만 둔다(키: `bus_id`; 값: `lat`, `lng`, `speed`, `fixed_at`). 이력은 쌓지 않는다. 쓰기는 DB가 아니라 `Rails.cache`를 우선 검토한다(6절).
3. **투영**: 최신 위치를 노선 정류장 순서로 이은 선분에 투영해 현재 구간과 구간 안의 진행률을 구한다.
4. **계산**: `남은 거리 ÷ 구간 평균 속도`. 순간 속도는 신호 대기에서 크게 흔들려 쓰지 않는다. 구간 평균 속도는 방식 A의 통계에서 얻는다.
5. **거리**: 정류장 좌표만 있으므로 직선거리 × 보정 계수(예: 1.3). 정확도가 더 필요하면 도로 경로(외부 라우팅 서비스)가 필요하다.
6. **보정**: Geofence 진입·이탈 이벤트는 위치 추정을 정류장 기준으로 바로잡는 앵커로 계속 쓴다.

| 장점 | 한계 |
|---|---|
| 정류장 사이에서도 갱신된다 | Traccar 설정과 Rails 수신 경로가 추가된다 |
| 구간 진행률이 반영돼 더 정확하다 | 위치 신선도·종료 후 정리 같은 방어 로직이 필요하다 |
| | 차량이 늘면 수신 부하가 생긴다 (6절) |

## 3. 권장 순서

1. **1단계 (방식 A)**: 통계 테이블과 ETA 계산을 추가한다. 표본이 부족하면 지금의 "N개 정류장 남음"으로 폴백한다.
2. **2단계**: 예측 시각과 실제 진입 시각의 오차를 로그로 쌓아 정확도를 잰다.
3. **3단계 (방식 B)**: 오차가 크면 위치 전달을 붙여 구간 안 진행률을 반영한다. 이때도 A의 통계는 그대로 쓴다.

방식 B는 A를 대체하지 않고 A 위에 얹는다. 처음부터 B만 만들면 구간 평균 속도 통계가 없어서 결국 A를 다시 만들어야 한다.

## 4. 승객 웹 메시지 정의

승객 화면(`/stops/:stop_id/routes/:route_id`)의 파란 패널은 5초마다 `ArrivalPresenter`가 만든 값으로 갱신된다. 문구는 `config/locales/ko.yml`의 `arrivals.status.*`에 있다. 맨 앞 버스(`primary`)가 큰 글씨와 작은 글씨를 정하고, 나머지 버스는 한 줄 요약으로 나온다.

### 상태별 큰 글씨 (두 줄)

| 상태 | 조건 | 1줄 | 2줄 | 상태 |
|---|---|---|---|---|
| 정차 중 | 내 정류장 Geofence 안에 있음 (`arriving`) | 지금 정류장에 | 도착했습니다. | 기존 |
| 곧 도착 | 접근 중이고 추정 1분 미만 | 곧 | 도착합니다. | **신규** |
| N분 후 도착 | 접근 중이고 추정 1분 이상 (분 단위 올림) | 약 N분 후 | 도착 예정입니다. | **신규** |
| 이동중 (N개 정류장 남음) | 접근 중이지만 구간 통계 부족(ETA 없음) | N정거장 전에 | 있습니다. | 기존 |
| 위치 확인 중 | 운행 중이지만 아직 방문 기록 없음 (`unknown`) | 위치를 확인하는 | 중입니다. | 기존 |
| 지나감 | 내 정류장을 이미 지남 (`passed`) | 이 정류장을 | 지나갔습니다. | 기존 |
| 운행 없음 | 이 노선을 운행 중인 버스가 없음 | 운행 중인 버스가 | 없습니다. | 기존 |

### 작은 글씨 (큰 글씨 위 한 줄: 버스가 마지막으로 있던 정류장)

| 조건 | 문구 |
|---|---|
| 접근 중·지나감 + 마지막 방문이 열려 있음 | `{정류장} 정차 중` |
| 접근 중·지나감 + 마지막 방문이 닫힘(막 출발) | `{정류장} 출발` |
| 그 외 | (표시 안 함) |

### 두 번째 이후 버스 한 줄 요약 (`버스 번호 · 문구`)

| 상태 | 문구 | 상태 |
|---|---|---|
| 정차 중 | 정류장에 정차 중 | 기존 |
| 곧 도착 | 곧 도착 | **신규** |
| N분 후 도착 | 약 N분 후 도착 | **신규** |
| 이동중 (ETA 없음) | N정거장 전 | 기존 |
| 위치 확인 중 | 위치 확인 중 | 기존 |
| 지나감 | 이미 지나감 | 기존 |

### 표시 규칙

- ETA는 정확해 보이지 않게 분 단위로 **올림**한다(예: 181초 → 약 4분).
- 구간 통계가 부족하거나 위치가 오래되면 숫자를 숨기고 정류장 수나 "위치 확인 중"을 보여준다. 틀린 숫자보다 숫자가 없는 편이 낫다.
- 진행 바와 버스 아이콘 흐림은 남은 정류장 수 기준 그대로다(ETA와 무관).
- 영어 화면은 없다(`ko.yml`만 있음).
- 방식 B 도입 시 추가 예정: "지연 중"(현재 구간이 중앙값을 크게 넘김), 위치가 60초 넘게 오래됐을 때 "위치 확인 중". 아직 구현하지 않았다.

## 5. 데이터 모델 (안 — 방식 A는 테이블 없이 구현, 11절)

방식 A:

| 테이블 | 컬럼 | 용도 |
|---|---|---|
| `segment_stats` | `route_id`, `from_stop_id`, `to_stop_id`, `time_bucket`, `median_seconds`, `samples`, `updated_at` | 구간 소요 시간 통계. `time_bucket`은 시간대(예: 출퇴근/주간/야간)로 시작은 1개로 둔다 |
| `stop_dwell_stats` | `stop_id`, `median_seconds`, `samples` | 정류장별 정차 시간 (선택) |

- 통계는 운행 종료(`TripFinisher`) 시점에 그 운행의 방문 기록으로 갱신한다. 이상치(0초·수 시간)는 표본에서 제외한다.
- 이동 평균 대신 최근 N건의 중앙값을 쓴다. 한두 번의 지연에 흔들리지 않는다.

방식 B 추가:

| 저장소 | 값 |
|---|---|
| `Rails.cache` (키 `bus_position:<bus_id>`) | `lat`, `lng`, `speed`, `fixed_at` |

## 6. 서버 부하 (방식 B)

앱이 15m 이동 또는 10초마다 보내므로 차량당 초당 약 0.1건이다.

| 차량 수 | 위치 요청 |
|---|---|
| 10대 | 약 1건/초 |
| 50대 | 약 5건/초 |
| 200대 | 약 20건/초 |
| 500대 | 약 50건/초 |

- 운영 DB가 SQLite이고 Solid Queue가 Puma 안에서 같이 돈다. 위치마다 DB에 쓰면 쓰기 경합이 생기고 승객 화면 응답도 느려질 수 있다.
- 완화:
  - 최신 위치는 캐시에만 둔다. 재부팅으로 사라져도 10초 안에 복구된다.
  - 운행 중이 아닌 차량의 위치는 수신 즉시 버린다.
  - ETA는 위치가 올 때가 아니라 승객이 화면을 열 때 계산한다.
- 수백 대 이상이면 PostgreSQL 전환과 수신 프로세스 분리를 따로 검토한다.
- 위 수치는 추정치다. 실제 부하는 구현 후 측정한다.

## 7. 방어 로직 (필수)

| 문제 | 처리 |
|---|---|
| 꺼진 단말의 마지막 위치 | `fixed_at`이 60초 넘게 오래됐으면 ETA를 숨기고 "위치 확인 중" |
| 운행 종료 후 남은 위치 | `TripFinisher`에서 해당 차량의 캐시 위치를 비운다 |
| 이미 지나간 정류장 | ETA를 만들지 않는다 (`passed`) |
| 오프라인 후 몰려오는 과거 위치 | `fixed_at`이 현재보다 크게 과거면 버린다 (Traccar도 과거 시각 위치로는 이벤트를 만들지 않는다. `docs/future-improvements.md` 18번) |
| `sequence` 결번 | 값이 아니라 노선 안의 목록 순번으로 비교한다 (`RouteBusStatuses`와 동일) |
| 같은 노선 버스가 붙어서 운행 | 버스마다 따로 계산하고 정류장 기준으로 정렬해 보여준다 |

## 8. Traccar 설정 (방식 B)

- Traccar 코드는 고치지 않고 설정만 추가한다. 설정은 환경변수로 하며(`CONFIG_USE_ENVIRONMENT_VARIABLES`), 이름을 틀리면 오류 없이 무시된다 (`config/deploy.yml` 주석).
- 위치 전달 키는 `forward.enable`, `forward.type`, `forward.url`, `forward.header`로 알고 있다. 환경변수 이름은 `FORWARD_ENABLE` 등이다. **운영 이미지(`traccar/traccar:6.14.4`) 기준으로 키 이름을 먼저 확인해야 한다.** 설정 후에는 Rails에 요청이 실제로 오는지 반드시 확인한다.
- 수정 대상:
  - 운영: `config/deploy.yml`(Traccar accessory), `.kamal/secrets`(인증 헤더)
  - 로컬: `docker/traccar/traccar.xml`, `bin/traccar`
  - 문서: `docs/traccar-accessory.md`, `docs/traccar-integration.md`
- 인증은 이벤트와 같은 `X-Ingest-Token`을 쓴다. 수신 엔드포인트는 이벤트용 `TraccarEventsController`와 같은 방식으로 만든다(인증 실패 401, 그 외 항상 200 ack).
- 배포로 Traccar accessory를 재시작하면 위치·이벤트 수신이 잠깐 끊긴다.

## 9. 합의가 필요한 항목 (1번은 A만 구현하는 것으로 진행함)

1. 먼저 방식 A만 만들고 B는 오차 측정 후 결정할지.
2. ETA를 "N분"으로 보여줄 기준(최소 표본 수, 신뢰도)과 표시 방식(분 단위 올림, 범위).
3. 시간대 구분(출퇴근/주간/야간)을 1단계부터 넣을지.
4. 위치가 도로를 따라가지 않을 때의 거리 보정을 직선 × 계수로 둘지, 외부 라우팅을 쓸지.
5. 차량 규모 예상과 운영 서버 사양 (6절의 부하 판단 근거).

## 10. 검증 계획 (방식 B)

- 방식 A: 시뮬레이터(`docs/location-sampling-test.md`)로 여러 운행을 돌려 통계가 쌓이는지, 표본 부족 시 폴백이 되는지, 이상치가 제외되는지 테스트한다.
- 방식 B: 위치 수신 엔드포인트의 인증·형식 오류·과거 시각 위치 테스트. 신선도 60초 경계, 종료 후 정리, 지나간 정류장 처리를 각각 단위 테스트로 둔다.
- 정확도: 예측 도착 시각과 실제 진입 시각의 차이를 로그로 남겨 오차 분포를 본다. 실기기 시험은 별도로 한다(시뮬레이터는 GPS 오차와 정체를 재현하지 못한다).

## 11. 구현 현황 (방식 A)

| 구성 | 파일 |
|---|---|
| 구간 소요 시간 중앙값 | `app/services/segment_times.rb` — 끝난 운행 최근 30건의 방문 기록에서 계산, 10분 캐시 |
| 도착까지 추정 초 | `app/services/route_bus_statuses.rb` — `Status#eta_seconds` |
| 화면 문구 | `app/presenters/arrival_presenter.rb`, `config/locales/ko.yml` |
| 테스트 | `test/services/segment_times_test.rb`, `route_bus_statuses_eta_test.rb`, `test/presenters/arrival_presenter_eta_test.rb` |

**동작**
- 구간 시간 = 앞 정류장 이탈 → 다음 정류장 진입. 이웃한 정류장 쌍만 센다. 한 시간을 넘는 값은 이상치로 버린다.
- 구간마다 표본이 3건(`MIN_SAMPLES`) 이상이어야 한다. 내 정류장까지 가는 구간 중 하나라도 부족하면 ETA는 없다(`nil`).
- 추정 = (정차 중이면 남은 정차 시간) + 구간 시간들 + 중간 정류장 정차 시간. 막 출발했다면 첫 구간은 이미 지난 시간만큼 뺀다(0 아래로 내려가지 않음).

**설계(2~5절)에서 달라진 점**
- 통계 테이블(`segment_stats`)을 만들지 않고, 요청 때 최근 운행에서 계산해 캐시한다. 마이그레이션과 갱신 로직이 필요 없고 통계가 낡을 일이 없다. 노선당 쿼리가 한 번이다.
- 정차 시간은 정류장별 통계 대신 고정값 20초(`DWELL_SECONDS`)를 쓴다.
- 표본 부족 시 거리 기반 가정 속도로 메우지 않고 ETA를 숨긴다. 그래서 **운행 이력이 쌓이기 전(구간당 3운행 이상)에는 기존 "N정거장 전" 화면 그대로**다.
- 시간대(출퇴근/주간/야간) 구분과 "지연 중" 표시는 하지 않았다.
- 구현하면서 오차 로그는 아직 넣지 않았다(3단계 판단용 — 방식 B 도입 전에 필요).
