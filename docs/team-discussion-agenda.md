## 안건 1. Traccar의 역할

**쟁점**: Traccar 서버를 앞으로도 필수 구성요소로 쓸 것인가, Rails가 GPS 수집을 대체할 것인가.
PR 기획서는 "Traccar의 핵심 GPS 수집 기능을 Rails로 대체"하고 병행 비교 후 단계적으로 전환하는 것을 목표로 한다. 재작성은 `product_requirements.md`에 따라 Traccar의 Geofence·그룹·기기 관리에 의존한다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. Traccar를 유지하고 필수로 둔다** (재작성 방향) | 검증된 GPS 수신·Geofence 판정·기기 관리를 그대로 쓴다. Rails가 단순하다(좌표 저장 없음). 기존 운전자 앱(Traccar Client SDK)과 호환된다. 요구사항 문서와 일치한다 | Java 서버를 별도로 운영해야 한다(실측: 기기 100대 규모에서 메모리 약 250~350MB, CPU 한 코어의 10~15%. 부록의 측정 결과 참고). Traccar가 멈추면 관리자의 등록·수정·배정이 안 된다(운행 시작·종료는 Traccar와 무관하게 되도록 고쳤다 — `future-improvements.md` 9번 해소). Rails↔Traccar 동기화 코드가 많다 |
| **B. Rails가 수집을 대체한다** (PR 방향) | 구성요소가 Rails 하나라 운영·배포가 단순하다. 앱이 Rails로 직접 전송해 중간 서버가 없다. 판정 규칙을 우리가 완전히 통제한다 | 수신·인증·유효성·정류장 판정·기기 관리를 직접 구현하고 유지해야 한다. 규모가 커졌을 때 SQLite 쓰기 경합이 미검증이다(PR 측정은 초당 5건 수준). 요구사항 1번(Geofence)을 바꿔야 한다 |
| **C. 병행하며 점진 전환한다** (PR 기획서의 단계 계획) | 위험을 나누고 두 방식을 실측으로 비교할 수 있다 | 두 경로를 모두 유지해야 한다. 같은 정류장 도착이 두 규칙으로 중복·불일치 판정될 수 있어 정책이 필요하다. 문서·운영이 복잡해진다 |

**영향**: 안건 2·3·4·9를 거의 결정한다.
**참고 의견**: 실측상 Traccar 자체가 소형 서버에 못 들어가는 것은 아니다(부록 측정). 메모리 부담은 결정적인 이유가 되기 어렵고, 요구사항 문서와의 일치·직접 구현해야 하는 범위·운영 구성요소 수가 더 큰 기준이다.

**결정 기록 (2026-10-23)**: **A. Traccar를 유지하고 필수로 둔다.**

## 안건 2. 정류장 도착/출발을 판정하는 방식

**쟁점**: 버스가 정류장에 들어가고 나간 것을 누가, 어떤 규칙으로 판정하는가. (안건 1과 연동되지만 별도로 정할 수 있다.)

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. Traccar Geofence 이벤트를 기록한다** (재작성) | 판정을 Traccar가 하므로 Rails 코드가 작다. 좌표를 저장하지 않아도 된다. 요구사항 1번과 일치한다. 노선별 그룹으로 다른 노선 버스의 이벤트를 걸러낸다 | Traccar 의존. 위치가 늦게 도착하면 이벤트가 사라진다(`future-improvements.md` 18번). 정류장 안에서 운행을 시작하면 첫 출발이 기록되지 않는다(20번). "곧 도착(접근)" 이벤트가 없다 |
| **B. Rails가 GPS 거리로 판정한다** (PR의 `StopEventDetector`: 접근 200m / 도착 30m / 출발 100m) | Traccar 없이 동작한다. "접근" 이벤트로 도착 임박 알림이 가능하다. 반경을 자유롭게 조정할 수 있고, 저장된 이력으로 재계산·디버깅할 수 있다 | 매 GPS마다 해당 버스 노선의 모든 정류장과 거리를 계산한다(정류장 수에 비례). 코드상 같은 버스·정류장·이벤트 유형은 1시간에 한 번만 기록되어, 1시간 안의 재방문(순환·왕복 노선)이 누락될 수 있다. 판정 규칙을 직접 유지·검증해야 한다. 위치 이력 저장이 필수다(안건 3) |
| **C. 이벤트 소스를 교체 가능하게 한다** (방문 기록은 하나, 입력은 Traccar 이벤트와 Rails 판정 둘 다) | 두 방식을 비교하며 점진 전환할 수 있다. 어느 쪽으로 가든 방문 기록·승객 화면은 그대로다 | 구현량이 늘고, 두 소스가 동시에 켜지면 중복 판정을 막는 규칙이 필요하다. 어떤 소스를 신뢰할지 정해야 한다 |

**영향**: 방문 기록(`stop_visits`) 테이블의 입력 방식, 위치 이력 저장 여부.
**참고 의견**: C는 안건 1에서 병행을 택했을 때만 의미가 있다. 한쪽으로 정했다면 A 또는 B 중 하나가 단순하다.

**결정 기록 (2026-10-23)**: **A. Traccar Geofence 이벤트를 기록한다.**

## 안건 3. GPS 좌표를 Rails가 저장할 것인가

**쟁점**: 좌표를 얼마나, 얼마 동안 Rails DB에 둘 것인가. 저장량과 위치정보 처리 책임이 걸려 있다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. 저장하지 않는다** (재작성) | 쓰기량이 0이라 DB 부담이 없다. 위치정보 보존·삭제 정책 부담이 줄어든다. 구조가 단순하다 | 지도에 버스를 점으로 표시할 수 없다. 정류장 사이 위치·수신 지연을 보여줄 수 없다. 좌표가 필요해지면 Traccar에 조회해야 한다 |
| **B. 버스당 현재 위치 1건만 둔다** | 지도 표시와 "마지막 수신 시각" 표시가 가능하다. 저장량이 거의 없다 | 이력 기반 분석·재계산이 불가능하다. Traccar를 쓰면 같은 값이 두 곳에 있다 |
| **C. 이력을 24시간 보존한다** (PR: 위치 이력·GPS 로그 24시간, 정류장 이벤트 7일, 구간 통계 90일) | 재계산·디버깅·통계가 가능하다. 지도와 판정(안건 2의 B)의 기반이 된다 | 쓰기량이 크다(PR 가정: 초당 5건). 보존·삭제 잡이 필요하다. 위치정보의 수집 목적·보존·열람 범위를 문서화해야 한다(PR 기획서 6번). SQLite 쓰기 경합이 규모에 따라 문제가 될 수 있다(미확인) |

**영향**: 안건 2의 B를 고르면 C가 사실상 필수다. 안건 4의 지도는 B 이상이 필요하다.
**참고 의견**: 지도가 필수가 아니고 안건 2에서 A를 고르면 A로 충분하다.

**결정 기록 (2026-10-23)**: **A. 좌표를 저장하지 않는다.**

## 안건 4. 승객 화면의 범위 (지도·ETA)

**쟁점**: 승객에게 무엇을 보여줄 것인가. 현재 재작성은 "N개 정류장 남음, 어느 정류장에 정차 중/출발"의 텍스트 화면이다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. 정류장 단위 현황만** (재작성) | 요구사항 3번을 충족한다. 구현·유지가 단순하다. 좌표 저장이 필요 없다 | 직관성이 낮다. "몇 분 뒤 도착"이 없다 |
| **B. 노선 지도를 추가한다** (PR: Google/Kakao/OpenStreetMap 지원) | 시각적으로 이해하기 쉽다. OpenStreetMap은 API 키 없이 쓴다 | 좌표 저장이 필요하다(안건 3). 제공자를 여럿 지원하면 유지 비용이 든다. Google/Kakao는 API 키 발급과 도메인 제한 설정이 필요하다. PR은 키를 관리자 설정 화면에서 입력받아 `settings` 테이블에 저장한다(브라우저로 전달되는 값이지만 저장 시 암호화 여부는 확인하지 못했다) |
| **C. ETA(예상 도착 시간)를 추가한다** (PR: 구간 소요 통계 집계 기반 준비) | 승객이 가장 기대하는 정보다. 방문 기록의 출발→도착 쌍으로 계산할 수 있다 | 데이터가 충분히 쌓여야 정확해진다. 정확도 검증이 별도로 필요하다(PR 기획서도 "ETA 정확도는 별도 검증"으로 둠) |

B와 C는 함께 선택할 수 있다.
**참고 의견**: 데모·초기 운영은 A, 이후 C(ETA)를 B(지도)보다 먼저 두는 편이 데이터 재료 면에서 자연스럽다. 지도가 요구사항이면 OpenStreetMap 하나로 시작하는 방법도 있다.

**결정 기록 (2026-10-23)**: **A. 정류장 단위 현황만.** 지도·ETA는 MVP 이후.

## 안건 5. 정류장·노선·운행의 데이터 모델

**쟁점**: 정류장을 노선에서 독립시킬 것인가, 버스와 노선의 관계를 "배차"로 둘 것인가 "운행 시작 시 선택"으로 둘 것인가. 상세 근거는 `docs/data-model-rewrite.md`.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. 기존 모델을 유지한다** (정류장은 노선 종속, 배차 `route_buses`) | 기존 코드·운영 습관·데이터를 그대로 쓴다. 운전자 앱을 고칠 필요가 없다. PR과 충돌이 적다 | 여러 노선이 서는 정류장을 중복 등록하고 Geofence도 겹친다. 버스에 여러 노선을 배차하면 지금 어느 노선인지 모호하고, Traccar 기기는 그룹이 하나뿐이라 어긋난다. 기존 로직 결함 중 구조적인 것들이 남는다(`business-logic-review.md`) |
| **B. 새 모델을 채택한다** (정류장 독립 + `route_stops`, 운행 시작 시 노선 선택, `trips.route_id`) | 요구사항 3번(정류장 기준 노선 선택)을 충족한다. 구조적 결함 대부분이 해소된다. 부분 유니크 인덱스 등 DB 제약으로 정합성을 보장한다 | 운전자 앱에 노선 선택·운행 시작/종료를 추가해야 한다. 기존 DB와 호환되지 않는다. 지역 계층 등 기능 제거를 함께 결정해야 한다(안건 6) |
| **C. 정류장 독립만 채택한다** (배차는 유지) | 정류장 중복·Geofence 중복을 해결하면서 앱 수정은 미룰 수 있다 | 배차와 운행 시작 선택이 공존해 개념이 이중이 된다. 운행 노선이 모호한 문제가 남는다 |

**참고 의견**: 이 모델 개선은 수집 방식(안건 1·2)과 무관하게 적용할 수 있다. 수집 방식 논의와 분리해서 결정해도 된다.

**결정 기록 (2026-10-23)**: **B. 새 모델을 채택한다.** 단, 지역 계층(시·도/운행지역)을 MVP에 포함할지는 **추가 논의** (보류).

**수정 (2026-10-24)**: "운행 시작 때 노선 선택" 대신 **관리자가 차량 하나에 노선 하나를 고정 배정**하고 운전자는 노선을 고르지 않는다. 기기를 노선 그룹에 넣는 일은 배정할 때 한다 (`docs/data-model-rewrite.md` 6-3).

## 안건 6. 기존 기능을 어디까지 유지할 것인가

**쟁점**: 재작성은 요구사항에 없는 기능을 제거했다. 시·도/운행지역 계층, 좋아요, 다국어(영어), 서비스 소개 페이지. PR은 이를 유지한 채 위에 기능을 얹었다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. 모두 제거한다** (재작성) | 모델·화면이 가장 단순하다. 요구사항에 집중한다. 로직 결함(좋아요 카운터, 삭제 전파 등)이 함께 사라진다 | 쓰던 기능이 없어진다. 여러 지자체를 구분할 수단이 없다. 영어 지원이 없다 |
| **B. 모두 유지한다** (PR, `main`) | 기존 기능과 화면을 잃지 않는다. 변경 범위가 작다 | 결함이 남는다. 지역 계층이 모든 조회 경로에 끼어 모델이 복잡하다 |
| **C. 선택해서 유지한다** (예: 지역 계층·다국어만) | 필요한 것만 남긴다 | 어떤 기능을 남길지 기능별 판단이 필요하다. 남기는 만큼 새 모델과의 통합 작업이 든다 |

**기능별 판단 재료**: 지역 계층은 지자체가 늘어날 때 필요(사전 확인의 지자체 확대 여부). 좋아요는 요구사항에 없고 삭제 정책과 충돌했던 기능. 다국어는 외국인 이용 요구가 있을 때.
**참고 의견**: 기능별로 "지금 쓰는 사용자가 있는가"를 확인한 뒤 정하는 것이 안전하다.

**결정 기록 (2026-10-23)**: **C. 선택해서 유지한다.** 어떤 기능을 남길지는 **추가 논의** (보류).

## 안건 7. 운전자 앱과 기기 인증

**쟁점**: (a) 운전자 앱을 얼마나 바꿀 것인가. (b) 기기를 어떻게 인증할 것인가. 두 작업이 같은 약점을 갖는다. PR의 `/gps`는 `id` 파라미터만으로, 우리 운행 시작·종료 API는 `deviceId`만으로 버스를 식별한다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. 현재 방식을 유지한다** (식별자만) | 구현이 없다. 앱 수정이 없다 | 식별자는 OsmAnd 프로토콜로 평문 전송된다. 엿본 사람이 다른 버스의 위치·운행을 조작할 수 있다 |
| **B. 기기별 토큰을 발급한다** (PIN 등록 때 발급, 이후 요청에 사용) | 식별자 노출만으로는 조작할 수 없다. PR의 `devices` 테이블 스키마를 활용할 수 있다 | 앱·서버 모두 수정이 필요하다. Flutter SDK가 커스텀 헤더를 보내지 못해 PR이 인증을 뺀 이력이 있어 방법(파라미터·본문 등)을 정해야 한다 |
| **C. 네트워크 수준 제한** (TLS, Traccar 서버 IP 제한, 요청 제한) | 앱 수정 없이 위험을 줄인다 | 기기 단위 통제는 못 한다. 운영 설정에 의존한다 |

**함께 결정할 것**: 안건 5에서 B를 고르면 앱에 운행 시작/종료 호출이 필요하다(2026-10-24 수정으로 노선 선택 화면은 필요 없어졌다). 앱 담당자와 일정을 확인한다.
**참고 의견**: A는 로컬 데모까지만 안전하다. 외부에 노출하기 전에 B 또는 C가 필요하다.

**결정 기록 (2026-10-23)**: **추가 논의** (보류).

**진행 현황 (2026-10-24, 팀 결정이 아니라 구현 쪽 판단)**: 앱 변경 범위는 위 "함께 결정할 것"대로 구현했다 — 노선 선택 없음, 서버 기준 운행 시작·종료, 앱 재시작 시 자동 재개. 기기 인증은 **A(식별자만) 그대로**이며 외부에 노출하기 전에 B 또는 C가 필요하다. 로그인은 차량별 **1회용 PIN**으로 하고(번호판은 공개 정보라 쓰지 않는다), PIN과 서버 주소는 MVP에서 관리자가 운전자에게 직접 전달한다(서버 주소 직접 입력을 없애는 방법은 `future-improvements.md` 23번).

## 안건 8. 운행의 시작과 종료

**쟁점**: 운행(Trip)을 누가 만들고 닫는가. 기존 `main`에는 운행을 닫는 코드가 없어서 한번 열리면 영구히 남았다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. 운전자가 시작·종료한다** (재작성) | 어느 노선인지 확실하다. 앱 수정으로 구현된다 | 운전자가 종료를 잊으면 열린 채 남는다(`future-improvements.md` 3번). 운전자 조작이 늘어난다 |
| **B. 첫 GPS로 자동 생성하고 일정 시간 수신이 없으면 자동 종료한다** (PR: 마지막 GPS 후 10분) | 운전자 조작이 필요 없다. 앱 수정이 없다. 종료를 잊어도 정리된다 | 노선을 알 수 없다 — 버스에 배차된 노선이 여럿이면 어느 노선인지 추정이 필요하다. 오프라인으로 끊기면 실제 운행 중에도 종료될 수 있다 |
| **C. 명시적 시작 + 자동 종료를 함께 쓴다** | 노선이 확실하면서 종료를 잊어도 정리된다. 두 방식의 약점을 서로 보완한다 | 구현량이 가장 많다. 자동 종료의 기준 신호를 정해야 한다(GPS 시각 / 마지막 방문 기록 시각 / 운행 시작 후 경과) |

**참고 의견**: 안건 5의 B를 택하면 C가 가장 현실적이다. 자동 종료 잡 자체는 PR 구현을 참고할 수 있다.

**결정 기록 (2026-10-23)**: **C. 명시적 시작 + 자동 종료.** 자동 종료의 기준 신호와 시간은 미정.

**진행 현황 (2026-10-24)**: 명시적 시작·종료는 구현했다(운전자 앱 + 서버 `trips/start`·`end`). 자동 종료는 **미구현**이라 종료를 잊으면 운행이 열린 채 남는다. 관리자가 열린 운행을 강제로 닫는 기능도 없다(`future-improvements.md` 24번). 기준 신호와 시간을 정하면 구현한다.

## 안건 9. 인프라·운영 목표

**쟁점**: 어디서 무엇을 돌릴 것인가. DB와 구성요소 수.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. 소형 서버 1대, SQLite** (PR: Puma + Solid Queue + SQLite, 1 vCPU/1GB 목표) | 비용·운영이 가장 단순하다. PR은 초당 5건 수신 + 100명 폴링에서 p95 약 16ms, RSS 약 124~148MB를 측정했다(PR 작성자 측정값) | 쓰기 경합이 규모에 따라 문제가 될 수 있다(PR 측정 범위 밖은 미확인). Traccar를 같은 서버에 두면 메모리가 약 250~350MB 더 든다(부록 측정). Rails(약 150MB)와 합치면 1GB에서 여유가 크지 않다. 단 우리 재작성의 Rails 메모리는 측정하지 않았다 |
| **B. 서버 분리 또는 상향** (Rails + Traccar를 각각, DB를 MySQL/PostgreSQL로) | 여유 있는 용량과 장애 격리. 쓰기 경합 문제가 줄어든다. Traccar 공식 문서도 기본 H2를 운영에 권하지 않는다 | 비용·운영 부담이 늘어난다. 마이그레이션이 필요하다 |
| **C. 일단 SQLite로 시작하고 지표를 보고 전환한다** (PR 기획서의 운영 원칙) | 초기 비용이 낮고 실측으로 판단한다 | 전환 시점·기준(쓰기 지연, 잠금 오류율 등)을 미리 정해 두지 않으면 문제가 터진 뒤에 대응하게 된다 |

**참고 의견**: 안건 1의 결과를 본 뒤 정한다. C를 택한다면 전환 기준 지표를 함께 적어 둔다.

**결정 기록 (2026-10-23)**: **A. 서버 1대에서 Rails와 Traccar를 함께 실행하고 SQLite를 쓴다.**

## 안건 10. 두 작업의 통합 전략

**쟁점**: PR #21과 재작성 브랜치를 어떻게 처리할 것인가. 안건 1~9의 결과에 따라 달라지므로 마지막에 정한다.

**현재 충돌 상태** (임시 워크트리에서 실제 merge 시도): 텍스트 충돌 8개 파일(`traccar_controller.rb`, `bus.rb`, `routes.rb`, `schema.rb`, `docs/traccar-integration.md`, 컨트롤러 테스트, 그리고 한쪽이 삭제하고 한쪽이 수정한 `arrival_polling_controller.js`·`route_bus_selector.rb`). 나머지 57개 파일은 텍스트상 충돌은 없지만 PR 코드가 재작성에서 없앤 모델(지역, 배차, GPS 로그 등)에 의존해 합치면 동작하지 않을 가능성이 크다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. 재작성 방향으로 통일한다**. PR에서 필요한 부분만 새 모델에 맞게 다시 적용 | 새 모델의 결함 해소 효과를 얻는다. 요구사항 문서와 일치한다 | PR의 수집·판정·지도 작업 상당수가 쓰이지 않는다. 작성자의 작업이 재작업된다. 앱 수정이 선행되어야 실사용이 된다 |
| **B. PR 방향으로 통일한다**. 재작성의 모델 개선(정류장 독립, `trips.route_id`, 운행 시작 API, 등록 서비스, 삭제 정책)을 PR 위에 얹기 | 이미 큰 PR(테스트 144개, 부하 측정)을 활용한다. 앱 수정 없이 점진 전환이 가능하다 | Traccar Geofence 요구사항을 포기하거나 바꿔야 한다. 재작성의 이벤트 수신 부분(`StopVisitRecorder`, Traccar 그룹 동기화)은 쓰이지 않는다 |
| **C. 하이브리드**. 방문 기록의 이벤트 소스를 교체 가능하게 하고(안건 2의 C) 모델 개선은 공통으로 적용 | 양쪽 작업이 모두 일부 살아남는다. 점진 전환이 가능하다 | 설계·구현이 가장 크다. 두 소스의 중복 판정 정책이 필요하다. 합의가 어려울 수 있다 |
| **D. 병행 유지**. PR은 `main` 대상으로 계속 진행, 재작성은 데모·실험 브랜치로만 유지 | 즉시 결정하지 않아도 된다. 서로 방해하지 않는다 | 갈림이 길어질수록 통합 비용이 커진다. 한쪽이 `main`에 들어가면 다른 쪽이 더 크게 충돌한다 |

**어느 선택지든 먼저 할 수 있는 일**
- 의존성 보안 갱신(Rails 8.1.4, sqlite3, brakeman 등)은 두 작업과 독립적이다. 별도 PR로 `main`에 먼저 넣으면 양쪽의 충돌과 중복 작업이 줄어든다.
- PR #21에 방향 논의가 시작됐음을 알리는 코멘트(PR은 외부에 공개되는 공간이므로 팀 합의 후 작성).
- 개선점 문서(`future-improvements.md`)와 PR 기획서의 겹치는 항목(자동 종료, 구간 통계, 인증)의 작업 소유자 정하기.

**참고 의견**: 안건 1에서 Traccar를 유지하면 A, 대체를 택하면 B가 단순하다. 정하지 못했다면 D로 두되 의존성 갱신 분리와 기한을 정해 두는 것이 좋다.

**결정 기록 (2026-10-23)**: **미결.** 단기 목표가 "MVP를 먼저 한 바퀴 완성"이라서 PR #21의 내용은 거부가 아니라 그 이후 단계에서 검토한다.

## 부록. Traccar 컨테이너 자원 실측

Traccar 공식 이미지(`traccar/traccar:6`, 이미지 크기 476MB)를 Docker로 띄워 직접 측정했다 (2026-10-23, Apple Silicon의 Docker Desktop VM, 기본 H2 DB, 호스트 메모리 7.7GB·CPU 8개).
공식 문서에서 최소 사양 숫자는 찾지 못했다(Docker 안내 페이지에는 없고, FAQ 주소는 404였다). 아래는 우리가 잰 값이다.

| 조건 | 유휴 | 부하 중 최대 | 결과 |
|---|---|---|---|
| 메모리 상한 없음, 기기 50대 × 10초 간격(초당 5건) 60초 | 312MiB | 약 341MiB, CPU 5~16% | 실패 0건, 응답 p95 32ms |
| 위와 같은 환경에서 기기 100대 초당 50건 30초 | | 약 347MiB(순간 381MiB), CPU 21~60% | 실패 0건, 응답 p95 34ms |
| 메모리 상한 **512MB**, 초당 5건 30초 + 초당 50건 20초 | 218MiB | 254MiB, CPU 40% | 정상, OOM 없음 |
| 메모리 상한 **256MB**, 같은 부하 | 211MiB | 247MiB, CPU 44% | 정상, OOM 없음. 여유는 약 9MiB뿐 |

해석과 한계:
- CPU는 한 코어 기준 %이고, 초당 5건에서는 한 코어의 10~15% 정도다.
- 256MB에서도 버텼지만 여유가 거의 없다. 이미지는 JVM 힙 상한(`-Xmx`)을 지정하지 않고 `-XX:+ExitOnOutOfMemoryError`만 지정하므로(컨테이너 메모리의 일부가 기본 힙 상한이 된다), 메모리가 부족해지면 오류가 아니라 **프로세스가 종료**된다. 실제 운영은 512MB 이상을 권한다.
- 측정은 짧다(수십 초). **며칠 단위의 메모리·H2 DB 증가는 측정하지 않았다.**
- 정류장 Geofence와 이벤트 포워딩이 없는 상태의 측정이다. 이벤트가 있으면 약간 더 든다(미측정).
- 공식 이미지는 `JAVA_OPTS` 같은 환경변수로 JVM 옵션을 받는 구조가 아니다(ENTRYPOINT에 `java`가 고정). 힙을 직접 조정하려면 entrypoint를 덮어써야 하는데 이는 확인하지 않았다.
- Linux 서버에서의 수치는 다를 수 있다. 우리 Rails의 메모리는 이 측정에 포함하지 않았다.
