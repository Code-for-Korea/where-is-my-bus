## 0. 용어 풀이

위에서 아래로 읽으면 앞에서 설명한 말만 나오도록 순서를 정했다. "Traccar 용어" 열은 Traccar 화면과 서버 로그에서 같은 대상을 부르는 이름이다.

| 용어 | 코드 | Traccar 용어 | 쉬운 설명 |
|---|---|---|---|
| **Traccar** | - | Traccar | 폰이 보내는 위치를 받아 두고, 지정한 구역에 버스가 드나들면 알려주는 별도의 위치 추적 서버. 우리 서비스가 의존한다 |
| **위치 신호** | - | Position | 운전자 폰이 Traccar로 보내는 위치 정보. 우리 서버에는 저장하지 않는다 |
| **정류장** | `Stop` | - | 버스가 서는 장소. 이름과 위치(위도·경도)를 가진다 |
| **정류장 영역** | `Stop.traccar_geofence_id` | Geofence | 정류장을 등록하면 위치를 중심으로 자동으로 만들어지는 한 변 30m 정도의 네모난 구역. 버스가 이 구역에 들어가고 나가는 것으로 정류장 도착·출발을 판단한다. 관리자 화면에는 "정류장 영역"으로 보이고, Traccar 화면과 서버 로그에서는 **Geofence(지오펜스)**로 나온다 |
| **노선** | `Route` | Group | 버스가 다니는 길. 정류장들을 정해진 순서로 지난다 (예: 1번 노선). Traccar에서는 **그룹(group)** 으로 만들어진다 |
| **정차 순서** | `RouteStop.sequence` | - | 한 노선 안에서 정류장이 놓인 순서 (1번째, 2번째, …) |
| **차량 / 버스** | `Bus` | Device | 운전자가 아니라 **차량 한 대**를 가리킨다. 번호판으로 구분한다. Traccar에서는 **기기(device)** 로 만들어진다 |
| **배정** | `Bus.route_id` | - | 관리자가 차량 한 대에 노선 하나를 정해 두는 것. 운전자는 배정된 노선으로 운행한다 |
| **PIN** | `Bus.pin` | - | 차량마다 서버가 만들어 주는 6자리 숫자. 운전자가 앱을 처음 쓸 때 "이 폰은 이 차량이다"를 확인하는 비밀번호 역할 |
| **운행** | `Trip` | - | 차량이 한 번 출발해서 끝날 때까지의 한 번의 영업. 운전자가 시작·종료한다 |
| **정류장 방문 기록** | `StopVisit` | - | 어느 운행의 버스가 어느 정류장 영역에 **언제 들어갔고 언제 나갔는지**의 기록. 승객 화면의 근거 |

## 1. 한눈에 보기

### 누가 무엇을 할 수 있나

| | 관리자 | 운전자 | 승객 |
|---|---|---|---|
| **정류장** | 등록·수정·삭제 | 앱에서 이전·현재·다음 정류장 이름 확인 (운행 중) | 선택해서 조회 |
| **노선** | 등록·이름 수정·삭제 | 앱에서 배정된 노선 확인 (고르거나 바꿀 수 없음) | 선택해서 조회 |
| **노선의 정류장 구성** | 정류장 추가·제거, 순서 지정 | - | 자세히보기에서 순서 조회 |
| **차량** | 등록·수정·삭제, PIN 확인·재발급, 노선 배정 | 앱에 PIN으로 등록 (자기 차량만) | 번호만 보임 |
| **운행** | 현황 조회 (※ 강제 종료는 아직 없음) | 시작·종료 | 운행 중 여부만 조회 |
| **위치(GPS)** | 보지 않음 | 폰이 자동 전송 | 정류장 단위로만 조회 |
| **정류장 방문 기록** | 최근 기록 조회 | - (앱의 이전·현재·다음 정류장이 이 기록에서 나옴) | 화면의 근거로 간접 조회 |

### 서비스의 큰 흐름

1. 관리자가 정류장, 노선, 차량을 등록하고 차량에 노선을 배정한다.
2. 관리자가 차량의 **PIN과 서버 주소**를 운전자에게 직접 전한다.
3. 운전자가 앱에 PIN을 입력해 등록하고, 출근해서 "운행 시작"을 누른다.
4. 폰이 위치를 보내면 Traccar가 "버스가 정류장 영역에 들어갔다/나갔다"를 알려주고, 서비스가 방문 기록으로 쌓는다.
5. 승객이 정류장을 고르면 "그 노선 버스가 어느 정류장에 있고 몇 정거장 남았는지"를 본다.
6. 운전자가 "운행 종료"를 누른다.

**이유**: `product_requirements.md`의 MVP 기능 — 관리자가 정류장을 등록하고, 운전자가 GPS를 전송하며, 승객이 정류장 기준으로 버스 위치를 조회한다.

## 2. 주체별 정책

<a id="s2-1"></a>
### 2-1. 관리자

관리자는 데이터를 관리하는 사람이다. 웹의 관리자 화면(`/admin`)에서 일한다.

#### 로그인과 계정

| 항목 | 정책 |
|---|---|
| 로그인 | 이메일과 비밀번호. 비밀번호는 8자 이상 |
| 역할 | **운영자(operator)**만 관리자 화면에 들어갈 수 있다. **일반 사용자(member)**는 들어갈 수 없다 (승객 화면만 사용) |
| 가입 | 누구나 가입 화면에서 가입할 수 있다. **가장 먼저 가입한 사람이 운영자**가 되고 이후 가입자는 일반 사용자가 된다 |
| 비밀번호 분실 | 이메일로 재설정 링크를 받는 기능이 있다 |
| 계정 관리 | 관리자 화면에 사용자 목록·역할 변경 기능은 없다 |

- ※ 현재 구현은 "가입이 열려 있고 첫 가입자가 운영자"다. 서비스를 외부에 열기 전에 운영자 계정을 만드는 방법을 정해야 한다 → **[검토 필요 9](#review-9)**
- ※ 확인 필요: 운영 환경의 이메일 발송 설정은 아직 자리표시 값이라 비밀번호 재설정 메일이 실제로 가는지 확인하지 못했다.
- ※ 개발 확인용으로 만든 데모 운영자 계정(시드 데이터)이 있다. **운영 환경에는 만들면 안 된다.**
- **이유**: 로그인 방식은 기존 서비스의 것을 유지했다.

#### 할 수 있는 일

| 대상 | 할 수 있는 일 | 규칙 |
|---|---|---|
| 정류장 | 등록, 수정, 삭제 | 이름, 위도(-90~90), 경도(-180~180) 필수. 등록하면 정류장 영역이 자동으로 만들어진다 |
| 노선 | 등록, 이름 수정, 삭제 | 이름 필수, 같은 이름의 노선 불가 |
| 노선의 정류장 구성 | 정류장 추가·제거 | 추가할 때 **정차 순서 번호**를 직접 입력한다. 한 노선에 같은 정류장 두 번, 같은 순서 번호 두 번은 불가 |
| 차량 | 등록, 수정, 삭제 | 번호판 필수, 같은 번호판 불가. 표시용 번호(예: "1번")는 선택. 등록할 때 노선을 함께 배정할 수 있다 |
| 차량의 노선 | 배정, 다른 노선으로 이동, 배정 해제 | 노선 화면 또는 차량 화면에서 한다 ([3-4 참고](#s3-4)) |
| PIN | 차량 화면에서 확인, 재발급 | 직접 정할 수는 없다. 서버가 만든다 |
| 현황 | 대시보드에서 노선·정류장·차량 수, 운행 중인 버스, 최근 정류장 방문 10건(도착·출발 시각, 정차 중/출발함) 조회 | 방문 기록만 보는 별도 메뉴는 없다 (개발자 확인용은 서버 로그) |

**이유**: 등록·수정·삭제는 관리자만 한다는 것이 "주체: 관리자 — 데이터 관리"의 뜻이다.

#### 할 수 없는 일

| 못 하는 일 | 비고 |
|---|---|
| 정류장 방문 기록을 고치거나 지우기 | 기록은 자동으로만 쌓인다 |
| 운전자 대신 운행을 시작·종료하기 | ※ 아직 구현되지 않음. 운전자가 종료하지 못한 운행을 관리자가 닫을 방법이 없다 → **[검토 필요 7](#review-7)** |
| 노선 안에서 정류장 순서를 바꾸기 | 정류장을 제거한 뒤 원하는 순서로 다시 추가해야 한다 |
| PIN을 직접 정하기 | 보안상 서버가 무작위로 만든다 |
| 사용자 계정 관리 | 관리자 화면에 없다 |

#### 조건과 예외

- **운행 중인 차량은 노선 배정을 바꾸거나 풀 수 없다.** 운행이 끝난 뒤에 할 수 있다.
- **이력이 있는 것은 삭제할 수 없다.** 운행 기록이 있는 차량·노선, 정류장 방문 기록이 있는 정류장은 지울 수 없다. 차량이 배정된 노선도 지울 수 없다 (먼저 배정을 해제해야 한다).
- 정류장을 삭제하면 그 정류장이 속했던 노선에서도 빠진다 (방문 기록이 없을 때만 삭제 가능).
- 노선을 삭제하면 그 노선의 정류장 구성 정보도 함께 지워진다 (운행 기록과 배정 차량이 없을 때만).
- 정류장 이름·위치를 고치면 정류장 영역도 함께 바뀐다.
- 한 정류장에 여러 노선이 설 수 있다. 같은 정류장을 여러 노선에 추가하면 된다.
- 노선의 정류장 구성은 **운행 중에도 바꿀 수 있다.** ※ 현재 구현은 이를 막지 않는다 → **[검토 필요 8](#review-8)**

**이유**: 이력이 있는 것을 지우면 과거 운행 기록이 깨지고, Traccar에서만 지워지고 우리 서비스에는 남는 어긋남이 생길 수 있어 막았다. 운행 중 배정 변경을 막는 이유는, 진행 중인 운행의 노선과 Traccar의 노선 설정이 어긋나지 않게 하려는 것이다.

#### 실패했을 때

- 관리자가 등록·수정·삭제·배정을 하면 **Traccar에도 같은 변경이 반영**된다. Traccar 쪽이 실패하면 **우리 서비스의 변경도 취소**되고, 화면에 실패 이유가 나온다. 반쯤만 바뀐 상태를 만들지 않기 위해서다.
- 따라서 **Traccar 서버가 멈춰 있으면 관리자의 등록·수정·삭제·배정은 할 수 없다.** 조회는 된다.
- 삭제할 수 없는 경우에는 "삭제할 수 없습니다: …(이유)"가 나오고 아무것도 바뀌지 않는다. 삭제는 우리 서비스에서 먼저 확인하고, 가능할 때에만 Traccar의 것을 지운다.
- Traccar에서 사람이 직접 지우는 등으로 어긋났을 때는 각 화면의 **재동기화** 버튼으로 다시 맞춘다.
- 오류 문구는 "Traccar 노선", "Traccar 차량", "정류장 영역"처럼 쓴다. 실패 문구 끝에 붙는 Traccar의 원본 오류 메시지는 영어일 수 있다.

**이유**: "Traccar에 없는 정류장이 우리 서비스에만 있는 상태"를 허용하지 않는다는 원칙이다.

<a id="s2-2"></a>
### 2-2. 운전자

운전자는 자기 차량의 위치를 보내는 사람이다. **운전자 앱**으로 일한다. 운전자의 계정은 없고, 운전자는 "자기 폰이 등록된 차량"으로만 식별된다.

> 운전자 앱은 아래 정책대로 고쳐져 있다. 단위·화면 테스트와 iOS 시뮬레이터 시험은 마쳤다. ※ 확인 필요: **실제 휴대폰**(백그라운드·화면 꺼짐에서의 위치 전송, 배터리, GPS 정확도)은 아직 시험하지 못했다.

#### 할 수 있는 일

| 일 | 규칙 |
|---|---|
| **등록** | 앱을 처음 열 때 서버 주소와 차량의 **PIN**을 입력한다. 맞으면 이 폰이 그 차량으로 등록되고 앱이 기억한다. 등록할 때 차량 번호와 배정된 노선을 함께 받는다 |
| **운행 시작** | "운행 시작"을 누르면 **관리자가 배정해 둔 노선**으로 운행이 시작되고 폰이 위치를 보내기 시작한다. **서버에서 운행이 시작되었을 때에만** 위치 전송을 켠다 |
| **운행 종료** | "운행 종료"를 누르면 운행이 끝나고 위치 전송이 멈춘다. **서버에서 운행이 종료되었을 때에만** 멈춘다 |
| 위치 전송 | 운행하는 동안 폰이 자동으로 보낸다. 약 15m 움직일 때마다, 또는 10초마다 보내고, 멈춰 있어도 30초 안에는 보낸다 (※ 시뮬레이터에서는 정류장을 놓치지 않았으나 실기기는 아직 측정하지 못했다 — [시험 기록](location-sampling-test.md)) |
| 내 상태 보기 | 메인 화면에서 차량 번호, **배정된 노선**, 운행 중이면 서버가 보는 **이전 · 현재 · 다음 정류장**을 본다. 운행 중에는 10초마다 서버에서 새로 받는다 |

**이유**: 운전자 입장에서 할 일을 "등록 한 번, 시작, 종료"로 줄이는 것이 최소 공수 목표에 맞다.

#### 할 수 없는 일

- **노선을 고르거나 바꿀 수 없다.** 배정된 노선으로만 운행한다. (고장 등으로 노선이 바뀌어야 하면 관리자가 배정을 바꾼다.)
- PIN을 만들거나 바꿀 수 없다 (관리자만).
- 번호판을 입력해서 로그인할 수 없다. 번호판은 차에 붙어 있는 공개 정보라서, 번호만 알면 누구나 그 차량인 척할 수 있기 때문이다. 번호판은 화면에 보여주기만 한다.
- 다른 차량의 정보를 볼 수 없다.

#### 조건과 예외

- **노선이 배정되지 않은 차량은 운행을 시작할 수 없다.** 앱에 안내가 나온다.
- 이미 운행 중인 차량에서 "운행 시작"을 다시 눌러도 **새 운행이 만들어지지 않고** 진행 중인 운행이 이어진다. 앱을 껐다 켜거나 통신이 끊겨 다시 눌러도 안전하다.
- 운행 중이 아닐 때 "운행 종료"를 눌러도 오류가 아니다. 종료 응답이 유실돼 다시 누른 경우를 받아 주기 위해서다.
- **서버가 기준이다.** 서버 요청이 실패하면 앱은 상태를 바꾸지 않고 오류를 안내한다. 시작 요청이 실패하면 위치 전송을 켜지 않고, 종료 요청이 실패하면 "운행 중"을 유지하며 다시 누르면 재시도한다. 서버 운행은 시작됐는데 위치 권한 거부 등으로 위치 전송을 켜지 못하면 서버의 운행도 되돌린다.
- **앱을 껐다 켜도 이어진다.** 서버에 열린 운행이 있는데 앱이 운행 중이 아니면 앱이 **위치 전송을 자동으로 다시 켠다.** 반대로 서버의 운행이 이미 끝났는데 앱이 운행 중이면(예: 관리자 쪽 조치) 위치 전송을 멈추고 안내한다.
- 운행 시작·종료는 **Traccar 상태와 무관**하다. Traccar가 잠깐 멈춰도 운행을 시작하고 끝낼 수 있다.
- 운행을 끝내면 그 순간 "정류장 안에 있음"으로 남아 있던 기록은 **종료 시각에 나간 것으로** 닫힌다.

#### 실패했을 때

| 상황 | 결과 |
|---|---|
| PIN이 틀렸다 | 등록이 거부된다 |
| PIN을 5번 틀렸다 | 같은 접속지에서 **15분 동안** 등록 시도가 막힌다. ※ 확인 필요: 실제 운영 환경에서 이 제한이 동작하는지 확인하지 못했다 ([`future-improvements.md` 13번](future-improvements.md#13-register-속도-제한-동작-미확인)) |
| 이미 사용된 PIN이다 | 거부된다. 관리자에게 PIN 재발급을 요청해야 한다 |
| 차량 정보가 맞지 않는다(없어진 차량 등) | 운행 시작·종료가 거부되고 앱이 안내한다 |
| 노선이 배정되지 않았다 | 운행 시작이 거부되고 앱에 "배정된 노선이 없어 운행을 시작할 수 없습니다"가 나온다. 메인 화면에는 경고가 계속 보인다 |
| 서버에 연결할 수 없다 | 운행 시작·종료는 상태를 바꾸지 않고 오류를 안내한다. 이미 운행 중이던 폰은 위치를 계속 Traccar로 보내고, 화면의 노선·정류장 표시는 마지막 값을 유지한 채 다음 주기에 다시 시도한다 |

<a id="s2-3"></a>
### 2-3. 승객

승객은 로그인 없이 웹 화면에서 버스 위치를 보는 사람이다.

#### 할 수 있는 일

| 일 | 규칙 |
|---|---|
| 정류장 선택 | 처음 화면의 버튼을 누르면 나오는 선택 창에서 정류장을 고른다. 정류장 QR이 있다면 그 주소로 바로 들어온다 |
| 노선 선택 | 고른 정류장에 **노선이 여러 개** 서면 그중 기다리는 노선을 고른다. 노선이 하나뿐이면 이 단계를 건너뛴다. 노선마다 "운행 중 N대"가 보인다 |
| 버스 위치 조회 | 선택한 노선을 **지금 운행 중인 버스**가 어느 정류장에 있는지, 내 정류장까지 몇 정거장 남았는지 본다. **5초마다 자동으로 새로 고쳐진다** |
| 자세히보기 | 그 노선의 정류장 순서와, 버스가 어느 정류장에 있는지를 목록으로 본다 |
| 소개 페이지 | 서비스 소개 문구를 본다 |

#### 화면에 나오는 말 (현재 구현)

| 상황 | 화면 문구 |
|---|---|
| 내 정류장 앞쪽에서 오는 중 | 큰 글씨 "**N정거장 전에 있습니다.**" + 작은 글씨 "○○ 정차 중" 또는 "○○ 출발" (버스가 마지막으로 있었던 정류장) |
| 내 정류장에 서 있다 | "**지금 정류장에 도착했습니다.**" |
| 내 정류장을 이미 지났다 | "**이 정류장을 지나갔습니다.**" (버스 아이콘이 흐려진다) |
| 운행은 시작했지만 어느 정류장에도 아직 들어가지 않았다 | "**위치를 확인하는 중입니다.**" |
| 운행 중인 버스가 없다 | "**운행 중인 버스가 없습니다.**" |

- 같은 노선을 **버스가 여러 대** 운행 중이면 **내 정류장에 가장 가까운 버스**를 크게 보여주고 나머지는 "2번 · 2정거장 전"처럼 한 줄로 요약한다.
- 정차 중인 정류장에서는 "정차 중", 정류장 영역을 막 나갔으면 "출발"로 보인다.
- **노선에 한 곳도 포함되지 않은 정류장은 선택 목록에 나오지 않는다.**

**이유**: `product_requirements.md` — "승객은 특정 정류장을 기준으로 본인이 기다리는 노선에 해당하는 버스가 어느 정류장에 있는지 조회할 수 있다." 도착까지 걸리는 **시간(분)은 보여주지 않는다** — MVP는 정류장 단위 현황까지만 하기로 했다.

#### 할 수 없는 일

- 도착까지 몇 분 남았는지 볼 수 없다. (※ 소개 페이지의 일부 문구에는 "다음 버스 18분 후를 확인"이라고 적혀 있어 실제 기능과 어긋난다 → [`future-improvements.md` 22번](future-improvements.md#22-소개-페이지-문구가-eta를-약속함))
- 지도에서 버스를 볼 수 없다. 우리 서버가 위치 좌표를 저장하지 않으므로 정류장 사이의 정확한 위치도 알 수 없다.
- 좋아요를 누를 수 없고, 영어 화면은 없다.
- 로그인이 필요 없으므로 개인 설정을 저장하지 않는다.

#### 실패했을 때·한계

- 네트워크가 잠깐 끊겨도 마지막으로 받은 화면이 그대로 남고, 다음 주기에 다시 시도한다.
- 존재하지 않는 정류장이나, 그 정류장에 서지 않는 노선 주소로 들어오면 "없음"으로 처리된다.
- 버스가 터널 등에서 위치를 늦게 보내면 **정류장을 지나간 신호가 누락**되어 정류장을 건너뛴 것처럼 보일 수 있다 ([`future-improvements.md` 18번](future-improvements.md#18-오프라인-뒤-늦게-도착한-위치의-이벤트-손실)).
- 정류장 영역 **안에서 운행을 시작**하면 그 첫 정류장의 출발이 기록되지 않아, 다음 정류장에 들어갈 때까지 "위치를 확인하는 중"으로 보일 수 있다 ([`future-improvements.md` 20번](future-improvements.md#20-정류장-안에서-운행을-시작하면-첫-정류장-출발이-기록되지-않음)).

<a id="ch3"></a>
## 3. 객체별 정책

<a id="s3-1"></a>
### 3-1. 정류장

| 항목 | 정책 |
|---|---|
| 무엇인가 | 이름과 위치(위도·경도)를 가진 장소. Traccar의 "정류장 영역"과 1:1로 대응한다 |
| 만들기 | 관리자가 등록하면 위치 둘레(한 변 30m의 네모)에 정류장 영역이 자동 생성된다. Traccar 생성이 실패하면 정류장도 만들어지지 않는다 |
| 고치기 | 이름·위치를 고칠 수 있고, 정류장 영역도 함께 바뀐다 |
| 삭제 | **방문 기록이 하나라도 있으면 삭제할 수 없다.** 없으면 삭제되고 Traccar의 정류장 영역도 지워진다. 노선에서도 함께 빠진다 |
| 여러 노선 | 한 정류장이 여러 노선에 속할 수 있다 |
| 승객에게 | 어느 노선에도 속하지 않은 정류장은 보이지 않는다 |

- 정류장끼리는 **200~300m 이상 떨어뜨려 등록**하는 것이 좋다. 영역이 겹치면 한 번의 이동이 두 정류장에 동시에 기록될 수 있다. ※ 확인 필요: 이 거리 기준은 서비스가 강제하지 않고 시연 데이터를 기준으로 한 권고이다.
- **이유**: 정류장을 노선에서 독립시킨 것은 같은 장소를 노선마다 중복 등록하지 않기 위해서다. 이력이 있으면 삭제를 막는 이유는 [2-1 참고](#s2-1).

<a id="s3-2"></a>
### 3-2. 노선

| 항목 | 정책 |
|---|---|
| 무엇인가 | 이름을 가진, 정류장들의 순서 있는 묶음. Traccar의 "차량 그룹"과 1:1로 대응한다 |
| 만들기 | 관리자가 이름을 입력해 등록한다. 같은 이름 불가. Traccar 그룹이 자동 생성된다 |
| 고치기 | 이름만 고칠 수 있다 (Traccar 그룹 이름도 함께 바뀐다) |
| 삭제 | **운행 기록이 있거나 배정된 차량이 있으면 삭제할 수 없다.** 가능하면 노선의 정류장 구성 정보도 함께 지워진다 |
| 방향 | **왕복·순환은 따로 표현하지 않는다.** 방향이 다르면 노선을 따로 만든다 (예: "1번 상행", "1번 하행"). 같은 정류장을 두 번 지나는 순환 노선은 현재 표현할 수 없다 |

**이유**: 방향·순환은 MVP 범위를 넘는다고 보고 미뤘다 ([`future-improvements.md` 5번](future-improvements.md#5-노선-방향왕복순환-미모델링)).

<a id="s3-3"></a>
### 3-3. 노선별 정차 (노선 안의 정류장과 순서)

| 항목 | 정책 |
|---|---|
| 무엇인가 | "이 노선은 이 정류장을 몇 번째로 지난다"는 정보 |
| 추가 | 관리자가 노선 화면에서 정류장과 순서 번호를 골라 추가한다. 순서 번호는 1 이상의 정수이고 기본값은 마지막 번호 + 1이다 |
| 순서 변경 | ※ 아직 구현되지 않음 — 순서를 바꾸려면 정류장을 **제거한 뒤 다시 추가**해야 한다 (순서 번호를 중간에 끼워 넣거나 바꾸는 기능이 없다) |
| 제거 | 노선에서 정류장을 뺀다. 정류장 자체는 지워지지 않는다 |
| 번호에 빈 칸이 있어도 | 승객 화면의 "몇 정거장 남았는지"는 순서 **번호의 차이가 아니라 노선 안의 위치**로 센다. 번호가 1, 2, 5처럼 건너뛰어도 정확하다 |
| Traccar와의 관계 | 정류장을 노선에 추가하면 Traccar에서도 "이 노선의 버스는 이 정류장 영역의 출입을 알려달라"고 연결된다. 제거하면 연결이 해제된다. 연결에 실패하면 추가도 취소된다 |

**이유**: 노선별로 연결해 두면, 다른 노선 버스가 우연히 그 정류장 근처를 지나갈 때의 신호까지 받지 않아도 된다.

<a id="s3-4"></a>
### 3-4. 차량 (배정 노선과 PIN 포함)

| 항목 | 정책 |
|---|---|
| 무엇인가 | 버스 한 대. 번호판으로 구분하며 Traccar의 기기 하나와 대응한다 |
| 만들기 | 관리자가 번호판(필수), 표시용 번호(선택), 배정 노선(선택)을 입력해 등록한다. PIN과 기기 식별자는 서버가 자동으로 만든다. Traccar 기기 생성이 실패하면 차량도 만들어지지 않는다 |
| 번호판 | 같은 번호판을 두 번 등록할 수 없다 |
| 고치기 | 번호판, 표시용 번호, 배정 노선을 고칠 수 있다 |
| 삭제 | **운행 기록이 있는 차량은 삭제할 수 없다.** 없으면 삭제되고 Traccar의 기기도 지워진다 |

#### 배정 노선

- **차량 하나에는 노선 하나만** 배정한다.
- 배정은 관리자가 **노선 화면의 "배정 차량"**에서 하거나 **차량 화면의 "배정 노선"**에서 한다.
- 다른 노선에 이미 배정된 차량을 고르면 **그 노선에서 이 노선으로 옮겨진다.** (선택 목록에 "현재: 2번 노선"처럼 지금 어디 배정인지 함께 보인다.)
- 배정하면 Traccar 기기가 그 노선의 그룹으로 옮겨진다. 해제하면 그룹에서 빠진다. Traccar 반영이 실패하면 배정 변경도 취소된다.
- **운행 중인 차량은 배정을 바꾸거나 풀 수 없다.**
- 노선이 배정되지 않은 차량은 운행을 시작할 수 없다. 차량 화면에는 "배정된 노선이 없습니다 — 노선을 배정해야 운전자가 운행을 시작할 수 있습니다"가 경고로 보인다.
- 고장 등으로 대체 차량을 투입할 때는 관리자가 배정을 바꾼다 ([4장 참고](#ch4)).
- **이유**: 한 차량이 하루 안에 노선을 바꿔 달리는 일이 드물다고 보았고(팀 판단), 이렇게 하면 운전자 앱에 노선 고르는 화면이 필요 없어 MVP 공수가 줄며, Traccar의 기기가 그룹을 하나만 가질 수 있다는 제약과도 맞는다.

#### PIN (운전자 등록용 비밀번호)

| 항목 | 정책 |
|---|---|
| 만들기 | 차량을 등록할 때 서버가 **6자리 숫자**를 무작위로 만든다. 다른 차량의 PIN과 겹치지 않는다 |
| 전달 | 관리자가 차량 화면에서 PIN을 확인해 **서버 주소와 함께 운전자에게 직접 전한다.** 전화, 메신저, 대면 등 수단은 정해져 있지 않다. 자동으로 보내지지 않는다 (MVP) |
| 사용 | 운전자가 앱 첫 실행 때 서버 주소와 PIN을 입력한다 |
| **한 번만** | 등록이 성공하면 그 PIN은 **사용된 것**으로 처리되어 다시 쓸 수 없다. 다른 폰이 같은 PIN으로 등록하려 하면 거부된다 |
| 재발급 | 폰을 잃어버리거나 바꿀 때, PIN이 유출됐을 때 관리자가 재발급한다. **옛 PIN은 즉시 무효**가 되고 "앱 등록 여부"가 미등록으로 돌아가 새 PIN으로 다시 등록할 수 있다 |
| 무작위 대입 방지 | 틀린 PIN을 5번 입력하면 같은 접속지에서 15분 동안 시도가 막힌다 (※ 운영 환경 동작 확인 필요) |
| 화면 표시 | PIN은 관리자 화면에 그대로 보인다. 운영자 계정을 가진 사람은 누구나 볼 수 있다 |

- **이유**: 번호판은 공개 정보라 로그인에 쓰면 안전하지 않다. PIN은 차량마다 다르고 한 번만 쓸 수 있어 "이 폰이 이 차량이다"를 확인하는 수단이 된다. 서버 주소를 사람이 직접 입력해야 하는 불편은 알고 있으며 후속 개선으로 미뤘다 (`future-improvements.md` 23번, **[검토 필요 5](#review-5)**).

<a id="s3-5"></a>
### 3-5. 운행

| 항목 | 정책 |
|---|---|
| 무엇인가 | 한 차량이 한 노선으로 한 번 달리는 영업 기록. 시작 시각과 종료 시각을 가진다 |
| 시작 | 운전자가 앱에서 "운행 시작". 노선은 **그 순간 차량에 배정된 노선**으로 정해지고 이후 바뀌지 않는다 |
| 종료 | 운전자가 앱에서 "운행 종료" |
| 한 번에 하나 | 한 차량은 **동시에 운행이 하나만** 있을 수 있다. 시스템이 이를 보장한다 |
| 자동 종료 | ※ **아직 구현되지 않음** — 정책은 "운전자가 종료를 잊어도 일정 조건에서 자동으로 닫는다"이지만 기준과 시간을 아직 정하지 못했다 → **[검토 필요 4](#review-4)**. 그때까지는 종료를 잊으면 **열린 채 남는다** |
| 종료 때 하는 일 | 열려 있던 "정류장 안에 있음" 기록을 종료 시각에 나간 것으로 닫는다 |
| 보존·삭제 | 운행 기록을 지우는 기능은 없다. 보존 기간 정책도 아직 없다 → **[검토 필요 10](#review-10)** |
| 관리자 | 대시보드에서 운행 중인 버스를 볼 수 있다. ※ 아직 구현되지 않음: 관리자가 운행을 강제로 닫는 기능 → **[검토 필요 7](#review-7)** |

**이유**: 운전자가 직접 시작·종료하게 한 것은 어느 노선의 운행인지를 확실히 하기 위해서이고, 자동 종료를 더하기로 한 것은 종료를 잊는 경우를 보완하기 위해서다.

<a id="s3-6"></a>
### 3-6. 정류장 방문 기록

| 항목 | 정책 |
|---|---|
| 무엇인가 | "어느 운행의 버스가 어느 정류장 영역에 언제 들어가고 언제 나갔는지"의 기록 |
| 어떻게 생기나 | 사람이 입력하지 않는다. Traccar가 "정류장 영역에 들어갔다/나갔다"를 알려주면 서비스가 자동으로 만든다. 우리 서버는 GPS 좌표를 따로 저장하지 않는다 |
| 쓰임 | 승객 화면과 운전자 앱의 "이전·현재·다음 정류장"의 근거. 관리자 대시보드에는 최근 10건이 보인다 |
| 고치기·삭제 | 관리자도 고치거나 지울 수 없다 (운행이 지워질 때만 함께 지워지는 구조인데 운행을 지우는 기능이 없다) |
| 정류장 삭제와의 관계 | 방문 기록이 있는 정류장은 삭제할 수 없다 |

#### 기록하지 않고 무시하는 신호

| 상황 | 이유(쉬운 설명) |
|---|---|
| 진행 중인 운행이 없는 차량의 신호 | 운행 전·후에 차고지 근처를 지나가는 것을 기록하지 않기 위해 |
| 그 운행의 노선에 속하지 않은 정류장의 신호 | 다른 노선의 정류장 근처를 우연히 지나간 것을 기록하지 않기 위해 |
| 운행 시작 시각보다 이전의 신호 | 지난 운행의 늦게 도착한 신호가 새 운행에 섞이지 않게 하기 위해 |
| 같은 신호가 두 번 도착 | 한 번만 기록한다 (중복 방지) |
| 이미 "정류장 안"으로 기록된 곳에 또 "들어갔다"가 온 경우 | 이상 상황으로 보고 기록하지 않는다 |
| 열려 있는 기록이 없는데 "나갔다"가 온 경우 | 기록하지 않는다 (정류장 안에서 운행을 시작한 경우 포함 — 알려진 한계) |
| 알 수 없는 차량·정류장 | 무시한다 |
| 정류장 출입 외의 다른 종류의 알림 | 무시한다 |

- 무시한 신호도 Traccar에는 "정상 수신"으로 응답한다 (오류로 응답하면 Traccar가 같은 신호를 계속 다시 보내기 때문).
- 위치 신호가 시각 순서대로 오지 않거나 과거 시각이면 Traccar가 신호를 만들지 않는다. 그래서 **오프라인에서 모아 두었다가 한꺼번에 보낸 위치**는 정류장 통과가 기록되지 않을 수 있다.
- ※ 확인 필요: 위치 좌표 이력은 우리 서버에는 없지만 **Traccar 서버에는 쌓인다.** 보존 기간과 열람 범위는 아직 정하지 않았다 → **[검토 필요 10](#review-10)**

<a id="ch4"></a>
## 4. 상황별 시나리오

| # | 상황 | 정책상 처리 |
|---|---|---|
| 1 | **운전자가 폰을 바꿨다 / 잃어버렸다** | 관리자가 차량 화면에서 PIN을 **재발급**하고 새 PIN과 서버 주소를 전한다. 옛 PIN과 옛 폰의 등록은 쓸 수 없게 해야 하는데 ※ 현재 구현은 옛 폰의 기기 식별자 자체를 무효화하지는 않는다(PIN만 새로 발급). 분실 폰의 악용 위험은 **[검토 필요 3](#review-3)**(기기 인증)에서 다룬다 |
| 2 | **차량이 고장 나 대체 차량을 투입한다** | 관리자가 (a) 대체 차량의 배정 노선을 고장 난 차량이 달리던 노선으로 바꾸고(대체 차량이 운행 중이 아닐 때), (b) 필요하면 고장 난 차량의 배정을 해제한다. 앱 수정은 필요 없다. **고장 난 차량의 운행이 열린 채 남아 있으면 그 차량의 배정은 풀 수 없다.** ※ 아직 구현되지 않음: 관리자 강제 종료 → **[검토 필요 7](#review-7)** |
| 3 | **운전자가 운행 종료를 잊었다** | ※ 자동 종료가 아직 없으므로 운행은 열린 채 남는다. 승객 화면에는 그 차량이 계속 운행 중(위치 확인 중이거나 마지막 정류장 근처)으로 보일 수 있다. 앱을 다시 열면 열린 운행이 이어지므로(위치 전송 자동 재개), 앱에서 직접 종료한 뒤 필요하면 새로 시작해야 한다 |
| 4 | **노선이 배정되지 않은 차량이 운행을 시작하려 한다** | 시작이 거부된다. 운전자 앱에는 "배정된 노선이 없습니다"가 보여야 하고, 관리자는 차량 화면에서 노선을 배정한다 |
| 5 | **Traccar 서버가 잠깐 멈췄다** | 관리자의 등록·수정·삭제·배정은 할 수 없다(변경은 취소되고 이유가 표시된다). 운전자의 운행 시작·종료는 된다. 다만 정류장 출입 신호를 받지 못하므로 **버스 위치가 갱신되지 않고** 승객 화면은 마지막으로 알고 있던 상태를 보여준다 (※ 오래된 정보가 그대로 보일 수 있다) |
| 6 | **우리 서버가 잠깐 멈췄다** | 운전자의 운행 시작·종료와 승객 화면이 모두 안 된다. 폰이 Traccar에 보내는 위치는 계속 간다. ※ 확인 필요: 그동안 Traccar가 보낸 정류장 신호를 우리 서버가 복구된 뒤 다시 받는지는 확인하지 못했다 |
| 7 | **같은 노선을 버스 두 대가 운행한다** | 지원한다. 승객 화면은 내 정류장에 가장 가까운 버스를 대표로 보여주고 다른 버스는 한 줄 요약으로 보여준다 |
| 8 | **노선을 지우고 싶다** | 먼저 그 노선의 배정 차량을 모두 해제한다. 그래도 운행 기록이 한 번이라도 있으면 지울 수 없다 |
| 9 | **잘못 등록한 정류장을 지우고 싶다** | 방문 기록이 없으면 지울 수 있다. 버스가 한 번이라도 들어간 정류장은 지울 수 없다 → **[검토 필요 10](#review-10)** |
| 10 | **운행 중에 노선의 정류장 구성을 바꿨다** | ※ 현재 구현은 막지 않는다. 바꾸면 진행 중인 운행의 승객 화면에 바로 반영된다. 허용할지는 **[검토 필요 8](#review-8)** |
| 11 | **운전자가 PIN을 다른 사람에게 알려주었거나 누가 먼저 입력해 버렸다** | 이미 사용된 PIN은 거부된다. 관리자가 재발급해서 다시 전한다 |
| 12 | **관리자가 비밀번호를 잊었다** | 비밀번호 재설정 메일을 받을 수 있다. ※ 확인 필요: 운영 환경의 메일 발송 설정이 아직 없다 |
| 13 | **정류장 안에서 운행을 시작했다** | 그 정류장의 출발이 기록되지 않아 다음 정류장에 들어갈 때까지 "위치를 확인하는 중"으로 보일 수 있다 (알려진 한계) |
| 14 | **운행 중에 앱이 꺼졌다 / 폰이 재부팅됐다** | 앱을 다시 열면 서버에 열린 운행을 확인해 위치 전송을 자동으로 다시 켠다. 꺼져 있던 동안 위치는 전송되지 않았으므로 그사이 지난 정류장은 기록되지 않았을 수 있다 (※ 확인 필요: 폰이 앱을 백그라운드에서 얼마나 오래 살려 두는지는 실기기 시험 필요) |

<a id="ch5"></a>
## 5. 아직 결정되지 않은 것 (검토 필요)

팀이 이미 정하기로 보류한 것 1~6과, 이 문서를 쓰며 새로 드러난 것 7~10이다.

<a id="review-1"></a>
### [검토 필요 1] 지역 계층(시·도/운행지역)을 MVP에 넣을 것인가

- 현재: 새 구조에서 **제거**한 상태. (기존 서비스에는 있었다.)
- A. 넣지 않는다 — 구조가 단순하고 만들 것이 적다. 단, 지자체·지역이 여러 곳이 되면 구분할 방법이 없다.
- B. 넣는다 — 지역별로 노선·정류장을 묶을 수 있고 기존 구조와 같다. 단, 모든 조회·등록 경로에 지역이 끼어 모델과 화면이 복잡해지고 공수가 늘어난다.
- 판단 재료: 곧 여러 지자체가 쓸 예정인가, 승객이 지역을 먼저 고르는 화면이 필요한가.

<a id="review-2"></a>
### [검토 필요 2] 기존 기능 중 무엇을 남길 것인가

| 기능 | 현재 상태 | 남길 때 | 뺄 때 |
|---|---|---|---|
| 지역 계층 | 없음 | ([검토 필요 1](#review-1)) | |
| 좋아요 | 없음 | 승객 반응을 볼 수 있다. 단, 삭제 정책과 얽히던 기능이라 다시 설계해야 한다 | 단순하다 |
| 영어 화면 | 없음 | 외국인 이용자를 지원한다. 문구 번역을 계속 유지해야 한다 | 단순하다 |
| 소개 페이지 | 있음(복원됨) | 서비스를 알리는 곳이 생긴다. 단, 문구 일부가 실제 기능과 어긋난다 | 문구 정리 부담이 없다 |

<a id="review-3"></a>
### [검토 필요 3] 운전자 앱의 변경 범위와 기기 인증

- 현재: 운행 시작·종료를 **차량의 기기 식별자만**으로 요청한다. 이 식별자는 폰에서 Traccar로 위치를 보낼 때 평문으로 오가므로, 엿본 사람이 다른 차량의 운행을 조작할 수 있다.
- A. 현재 유지 — 추가 작업이 없다. 로컬·시험 단계까지만 안전하다.
- B. 기기별 비밀 값 발급 — 등록 때 앱에 비밀 값을 주고 이후 요청에 쓰게 한다. 안전하지만 앱·서버를 모두 고쳐야 한다.
- C. 네트워크 수준 제한(암호화 통신, 접속지 제한) — 앱을 거의 안 고치고 위험을 줄이지만 기기 단위 통제는 못 한다.
- 판단 재료: 외부 공개 전에 어디까지 막아야 하는가.

<a id="review-4"></a>
### [검토 필요 4] 운행 자동 종료의 기준과 시간

운전자가 종료를 잊었을 때 운행을 자동으로 닫는 규칙. ※ 아직 구현되지 않음.

| 기준 | 장점 | 단점 |
|---|---|---|
| Traccar 기기의 마지막 위치 수신 시각이 N분 지났다 | "위치가 끊김"을 가장 정확히 나타낸다 | 터널·음영 지역에서 실제 운행 중인데 닫힐 수 있다 |
| 마지막 정류장 방문 기록 이후 N분 | 서비스 안의 정보만으로 판단한다 | 긴 구간·정체에서 잘못 닫힐 수 있다 |
| 운행 시작 후 최대 시간(예: 12시간) | 안전장치로 단순하다 | 이것만으로는 늦게 닫힌다 |

- 값 후보: 위치 끊김 N = 10분(참고: PR #21이 쓴 값), 최대 시간 = 12시간. **N과 최대 시간은 팀이 정해야 한다.**

<a id="review-5"></a>
### [검토 필요 5] 서버 주소를 운전자가 직접 입력하지 않게 하는 방법

- 현재(MVP): 관리자가 PIN과 서버 주소를 말로/메신저로 전하고, 운전자가 폰에서 직접 입력한다. 오타가 나기 쉽다.
- 후속 후보: QR 코드 스캔(입력 없음, 앱에 카메라 기능 필요), 앱에 서버 주소 내장(PIN만 입력, 주소가 바뀌면 앱 재배포), 링크 한 번 누르기(설정이 복잡), 짧은 접속 코드(중앙 서버 필요).
- 실기기 시험 이후에 정한다.

<a id="review-6"></a>
### [검토 필요 6] 서버·배포 조건

- 서버 1대에서 서비스 본체와 Traccar를 함께 돌리는 것까지는 정했다. **서버를 어디에 둘지, 사양(메모리 등), 접속 주소와 HTTPS 사용 여부는 정하지 못했다.**
- 참고: Traccar는 약 250~350MB, 서비스 본체는 약 150MB 수준(다른 작업자의 측정값)이라 1GB 서버에서는 여유가 크지 않을 수 있다.

<a id="review-7"></a>
### [검토 필요 7] 관리자가 운행을 강제로 종료할 수 있어야 하는가 (새로 발견)

- 현재: 운전자만 운행을 닫을 수 있고, 자동 종료도 없다. 폰이 고장 나거나 앱을 못 쓰는 상황에서는 운행이 영원히 열려 있고, 그 차량의 배정을 바꿀 수 없다.
- A. 관리자 화면에 "운행 강제 종료" 버튼을 둔다 — 문제를 직접 풀 수 있다. 화면 하나가 늘어난다.
- B. 자동 종료([검토 필요 4](#review-4))만으로 해결한다 — 만들 것이 적지만 자동 종료 전까지 기다려야 한다.

<a id="review-8"></a>
### [검토 필요 8] 운행 중에 노선의 정류장 구성을 바꿀 수 있어야 하는가 (새로 발견)

- 현재: 막지 않는다. 운행 중 정류장을 빼면 이미 기록한 방문이 어긋나 보이거나 승객 화면이 갑자기 달라질 수 있다.
- A. 허용한다 — 급한 수정을 바로 할 수 있다.
- B. 그 노선에 운행 중인 차량이 있으면 막는다 — 안전하다. 급할 때 모든 차량의 운행을 먼저 끝내야 한다.

<a id="review-9"></a>
### [검토 필요 9] 관리자 계정을 어떻게 만들고 관리할 것인가 (새로 발견)

- 현재: 가입이 누구에게나 열려 있고 첫 가입자가 운영자가 된다. 사용자 목록·역할 변경 화면은 없다.
- A. 가입을 닫고 운영자는 서버에서 직접 만든다 — 안전하다. 담당 개발자의 작업이 필요하다.
- B. 가입은 열어 두되 운영자 승격은 기존 운영자가 화면에서 한다 — 편하다. 화면을 새로 만들어야 한다.
- 데모 계정은 운영에서 반드시 제거해야 한다.

<a id="review-10"></a>
### [검토 필요 10] 이력과 위치 정보의 보존 기간 (새로 발견)

- 현재: 운행 기록·방문 기록은 지우는 기능도, 자동 삭제도 없다. 위치 좌표는 우리 서버에는 없지만 Traccar 서버에 쌓인다. 이력이 있는 정류장·차량·노선은 삭제할 수 없다.
- 정할 것: (a) 운행·방문 기록을 얼마나 보관하고 언제 정리할지, (b) Traccar의 위치 이력 보존 기간과 열람 범위, (c) 이력 때문에 지우지 못하는 항목을 어떻게 처리할지(이력도 함께 지움 / 숨김 표시 / 지금처럼 금지). 위치 정보를 다루므로 수집 목적·보존 기간·열람 범위를 안내 문서로 남기는 것이 권장된다.

## 6. 검토자에게 묻는 질문

"O/X"나 한 줄로 답해 주세요. 모르면 "모름"이라고 적어도 됩니다.

**관리자 정책**

1. 운영자만 관리자 화면에 들어갈 수 있고 일반 사용자는 못 들어가는 것이 맞나요? (O/X)
2. 이력이 있는 차량·노선·정류장을 지울 수 없게 막는 것이 맞나요? 지금 불편한 경우가 있나요? (O/X + 한 줄)
3. Traccar 반영이 실패하면 관리자의 변경도 함께 취소되는 것(그동안 등록·수정은 못 함)을 받아들일 수 있나요? (O/X)
4. 노선에서 정류장 순서를 바꾸려면 "제거 후 다시 추가"해야 하는 것을 MVP에서 받아들일 수 있나요? (O/X)
5. 운행 중인 차량의 노선 배정을 바꿀 수 없게 막은 것이 맞나요? (O/X)
6. 관리자가 운행을 강제로 종료하는 기능이 MVP에 필요한가요? (O/X) → [검토 필요 7](#review-7)
7. 운행 중에도 노선의 정류장 구성을 바꿀 수 있어도 되나요? (O/X) → [검토 필요 8](#review-8)
8. 관리자 가입은 닫고 운영자는 서버에서 직접 만드는 방식으로 가도 되나요? (O/X) → [검토 필요 9](#review-9)

**운전자 정책**

9. 운전자가 노선을 고르지 않고 **관리자가 배정한 노선으로만** 운행하는 것이 현장 사정에 맞나요? 하루 중 노선을 바꿔 달리는 일이 정말 없나요? (O/X + 한 줄)
10. 노선이 배정되지 않은 차량은 운행을 시작하지 못하게 하는 것이 맞나요? (O/X)
11. 로그인은 **PIN**(차량마다 다름, 한 번만 사용)으로 하고 번호판은 입력하지 않는 것이 맞나요? (O/X)
12. PIN과 서버 주소를 **관리자가 직접 전달**하는 방식(MVP)이 현실적인가요? 전달 수단(전화/메신저 등)은 무엇인가요? (한 줄)
13. 폰을 바꾸면 관리자가 PIN을 재발급하는 절차로 충분한가요? (O/X)
14. 운전자가 종료를 잊었을 때 자동으로 닫는 기준은 무엇이 좋을까요? "위치가 N분 끊기면" 이라면 N은 몇 분? 최대 운행 시간은? (한 줄) → [검토 필요 4](#review-4)

**승객 정책**

15. 승객 화면이 "도착까지 몇 분"이 아니라 "N정거장 전에 있습니다"로 보이는 것을 MVP에서 받아들일 수 있나요? (O/X)
16. 운행 중인 버스가 여러 대일 때 가장 가까운 버스를 크게, 나머지를 한 줄로 보여주는 방식이 맞나요? (O/X)
17. 화면 문구(위치 확인 중 / 지나갔습니다 / 운행 중인 버스가 없습니다 등)가 승객에게 이해되나요? 바꾸고 싶은 문구가 있나요? (한 줄)
18. 승객 화면에 지도가 MVP에 꼭 필요한가요? (O/X)

**범위와 운영**

19. 지역 계층(시·도/운행지역)이 MVP에 필요한가요? (O/X) → [검토 필요 1](#review-1)
20. 좋아요, 영어 화면, 소개 페이지 중 남겨야 할 것은 무엇인가요? (한 줄) → [검토 필요 2](#review-2)
21. 운행·방문 기록을 얼마나 오래 보관해야 하나요? 위치 정보 보존 기간에 대한 지자체 요구가 있나요? (한 줄) → [검토 필요 10](#review-10)
22. 서버를 어디에 둘 예정이고, 서비스 주소(도메인)와 HTTPS는 어떻게 되나요? (한 줄) → [검토 필요 6](#review-6)
